## 1. Цель и границы

Добавить Telegram-боту возможность:

- генерировать новые изображения из текстового промпта;
- редактировать загруженные фотографии по текстовой инструкции;
- последовательно редактировать предыдущий результат с сохранением контекста сессии;
- сбрасывать контекст командой или inline-кнопкой;
- работать как в личном диалоге с ботом, так и в группах;
- продолжать определённый старый результат через Telegram Reply;
- создавать **независимую ветку** от изображения другого участника группы, не меняя его исходную сессию;
- просматривать краткую историю своих генераций, повторно использовать результаты;
- контролировать расходы API, очереди и лимиты.

Не входят в MVP: собственный веб-интерфейс, платные подписки, публичная галерея, продажа кредитов, видеогенерация, GIF/SVG, сложный графический редактор с рисованием масок, полноценная система ролей сверх существующей авторизации, общая синхронизированная сессия всех участников чата.

## 3. Пользовательские сценарии

### 3.1. Личный чат

1. Текст без активной сессии → новая генерация по тексту.
2. Фотография + подпись → новая сессия редактирования исходного изображения.
3. Текст при активной сессии с успешной генерацией → редактирование последнего результата.
4. `/imagine <текст>` → явная новая генерация и новая активная сессия.
5. `/edit <текст>` → редактирование текущего результата либо изображения из Reply; при отсутствии исходника — понятное сообщение с инструкцией.
6. Reply на прежний результат бота с текстом → новая ветка от **указанного** результата, не обязательно от последнего. Ветка становится текущей для пользователя, предыдущая история остаётся доступной и не удаляется.
7. `/reset` или кнопка → закрыть активный контекст и убрать указатель на него; история остаётся.

### 3.2. Группа

1. Бот **не реагирует на произвольные обычные сообщения** группы.
2. Генерация запускается явной командой `/imagine` (включая `/imagine@BotName`).
3. Редактирование запускается командой `/edit` в Reply на фото/результат, подписью к фото или Reply на результат бота с текстовой инструкцией.
4. Контекст одного пользователя не смешивается с контекстом другого.
5. Reply на картинку другого участника, ранее созданную ботом, → новая **собственная** сессия/ветка. Сообщение-источник должно находиться в доступной этому участнику группе.
6. `/reset` сбрасывает только активную сессию автора команды **в текущем чате**.
7. При включённом Telegram privacy mode обработка команд/Reply должна работать без необходимости читать всю переписку группы. Учитывай реально доступные боту Update-события.

### 3.3. Несколько изображений (P1; архитектурно предусмотреть в P0)

- Принимать изображения как `Photo` и как `Document` (PNG/JPEG/WebP при поддержке сервиса); документы нужны для сохранения качества.
- В P1 поддержать альбом `MediaGroupId` с 2–4 изображениями как набор референсов, собирая его в коротком временном окне; максимальное количество — конфигурация. В P0 достаточно одного входного изображения, но модель данных и интерфейс провайдера сразу должны предусматривать коллекцию входных assets.
- Если пользователь прислал одиночное изображение без текста, предложить отправить инструкцию, сохранив временный черновик с TTL.
- Не интерпретировать второй референс как полную замену активной сессии без явного действия; предусмотреть кнопку/команду «Добавить референс» или простой черновик.
- Валидировать MIME, размер, доступность файла; конвертацию форматов и нормализацию ориентации выполнять безопасно.

### 3.4. Кнопки под результатом

Обязательно в P0:

- `🆕 Новая сессия` — сброс активного контекста **инициатора**, а не автора исходного результата и не всех участников группы.

После MVP (P1):

- `✏️ Продолжить` — подсказка Reply с вводом следующего промпта; по возможности привязка к `GenerationId`.
- `🔁 Переделать` — повторно выполнить тот же запрос с новым результатом **как отдельное дочернее ответвление**, без удаления оригинала; предупредить о новом платном вызове.
- `📄 Оригинал` — отправка изображения без Telegram-сжатия (`sendDocument`) или ссылка/файл, если уже допустимо.

`CallbackData` должна содержать компактный безопасный идентификатор действия и сущности, не секреты, не полный промпт. Каждый callback повторно проверяет пользователя, чат, права доступа, состояние и идемпотентность.

### 3.5. Команды

| Команда | Результат |
| --- | --- |
| `/imagine <prompt>` | Новая генерация с нуля |
| `/edit <prompt>` | Редактирование изображения из Reply или активной сессии |
| `/reset` | Закрытие личной активной сессии в текущем чате |
| `/history` | P1: последние N доступных пользователю результатов с пагинацией |
| `/settings` | P1: выбор модели/качества в разрешённых пределах |
| `/usage` | Лимиты, израсходованные запросы и ориентировочная стоимость |
| `/help` | Краткая инструкция для лички и группы |

Если команды в существующем боте конфликтуют с уже занятыми названиями, согласуй единую систему именования или используй пространство имён `/ai_*`. Не ломай старые команды.

## 4. Контекст, ветки и сброс

1. В БД сохранять **исходные и результирующие файлы, промпты и граф зависимостей**, а не полагаться только на `previous_response_id` стороннего API.
2. При продолжении передавать в Image Edit последний выбранный результат и новую инструкцию. При необходимости сохранения внешности/композиции разрешить дополнительно передавать оригинал и компактный системный контекст («сохрани узнаваемость», «измени только объект»). Не пересылать без необходимости всю историю бинарных изображений на каждом шаге.
3. Узел генерации неизменяем: повтор или новое редактирование создаёт новый узел с `ParentGenerationId`; старый результат никогда не перезаписывается.
4. `ActiveSession` — указатель для пары `(ChatId, UserId)`; он не является единственным способом доступа к истории. Reply по `MessageId` разрешает точный `GenerationId`. Когда пользователь создаёт ветку от старого узла, указатель переключается на неё; прежняя сессия сохраняется и может быть возобновлена другим Reply.
5. Когда пользователь продолжает **чужой** публичный результат, создаётся его собственная сессия с `SourceGenerationId` и собственной копией/ссылкой на разрешённый исходный asset. Не импортировать личные промпты, скрытые изображения или приватные сообщения автора.
6. `/reset`: пометить старую сессию закрытой, атомарно убрать/заменить активный указатель, увеличить версию контекста. **Не удалять** файлы и историю.
7. Выполняющийся job должен фиксировать `SessionVersionAtEnqueue`. Если за время выполнения произошёл reset, результат не должен менять новый `ActiveSession`/head. Задачи в очереди старой сессии можно отменять; уже отправленные внешние запросы нельзя считать бесплатно отменёнными.
8. Если ответ готов после reset, разрешён один из согласованных вариантов UX: отправить его с пометкой «результат предыдущей сессии» без активации либо не отправлять и отметить отменённым. По умолчанию — **отправить с пометкой**, если API уже вернул успешный результат.
9. Повторное нажатие кнопки, дубликат update и гонки не должны менять указатель контекста дважды или запускать двойной платный запрос.

## 5. Архитектура

Предпочтительна модульная реализация внутри текущего приложения:

```text
Telegram Update / Callback
  -> существующий Router / Command Handler
  -> AI Image Module (access, session resolution, validation)
  -> JobService (quota reservation + persistent enqueue)
  -> Background Worker (concurrency, retry, cancellation)
  -> IImageGenerationProvider -> OpenAI Image API
  -> IImageAssetStore (persistent binary files)
  -> Telegram Result Publisher + Usage Accounting
```

Предлагаемые интерфейсы (контракт по смыслу; имена могут адаптироваться к коду репозитория):

```csharp
public interface IImageSessionService
{
    Task<ImageSessionRef> GetOrCreateAsync(long chatId, long userId, CancellationToken ct);
    Task<ImageSessionRef> StartNewAsync(long chatId, long userId, CancellationToken ct);
    Task ResetAsync(long chatId, long userId, CancellationToken ct);
    Task<GenerationRef?> ResolveReplyAsync(long chatId, int messageId, long requesterId, CancellationToken ct);
}

public interface IImageGenerationProvider
{
    Task<ImageProviderResult> GenerateAsync(ImageProviderRequest request, CancellationToken ct);
    Task<ImageProviderResult> EditAsync(ImageProviderRequest request, CancellationToken ct);
}

public interface IImageAssetStore
{
    Task<StoredAsset> SaveAsync(Stream content, string contentType, CancellationToken ct);
    Task<Stream> OpenReadAsync(Guid assetId, CancellationToken ct);
    Task DeleteAsync(Guid assetId, CancellationToken ct);
}

public interface IImageJobService
{
    Task<EnqueueResult> EnqueueAsync(EnqueueImageCommand command, CancellationToken ct);
}
```

`ImageProviderRequest` должен содержать `Model`, `Prompt`, `InputAssets`, `Quality`, `Size`, `Complexity` (если поддерживается), `SafetyIdentifier`, `CorrelationId`; `ImageProviderResult` — бинарный результат/stream, фактически использованную модель, токены/usage (если предоставлены), provider request ID, информацию о причине отказа. В контракте **не должно быть** Telegram-специфичных типов.

Для MVP использовать OpenAI Image API (`/v1/images/generations`, `/v1/images/edits`). Обёртка провайдера должна позволять позже добавить Responses API с `previous_response_id` без изменения бизнес-слоя. Официальный OpenAI .NET SDK использовать, если он покрывает требуемые опции; иначе локально изолировать вызов через типизированный `HttpClient`.

## 6. Модель данных (логические сущности)

Не обязательно вводить все таблицы буквально, если аналогичные уже есть в проекте. Обязательна эквивалентная семантика.

### `ImageSession`

- `Id: Guid` (PK)
- `ChatId: long`, `OwnerUserId: long`
- `Status: Active | Closed`
- `HeadGenerationId: Guid?`
- `Version: int` (optimistic concurrency)
- `CreatedAtUtc`, `UpdatedAtUtc`, `ClosedAtUtc?`

### `ImageActiveSession`

- `ChatId: long`, `UserId: long` (составной unique key)
- `SessionId: Guid?`
- `UpdatedAtUtc`

### `ImageGeneration`

- `Id: Guid` (PK), `SessionId: Guid` (FK)
- `ParentGenerationId: Guid?` (предыдущий узел в этой сессии)
- `SourceGenerationId: Guid?` (ветка/импорт разрешённого результата из другой сессии)
- `Prompt: text`, `Mode: Generate | Edit`, `Model`, `Quality`, `Width`, `Height`
- `Status: Pending | Running | Completed | Failed | Cancelled`
- `ResultAssetId: Guid?` (FK), набор `InputAssetIds` через отдельную связь
- `CreatedAtUtc`, `CompletedAtUtc?`, `ErrorCode?`

### `ImageAsset`

- `Id: Guid` (PK), `StorageKey`, `ContentType`, `SizeBytes`, `Sha256`, `Width`, `Height`
- `CreatedAtUtc`, `ExpiresAtUtc?`, `DeletedAtUtc?`
- Допустимые origin/visibility/владелец по модели доступа проекта
- По возможности `TelegramFileId` как **кеш**, а не единственный источник файла

### `ImageTelegramMessage`

- `(ChatId, MessageId)` (unique key)
- `GenerationId`, `AssetId`, `MessageRole: Result | Preview | Source`
- Позволяет разрешать Reply на конкретную генерацию без анализа текста сообщения

### `ImageJob`

- `Id`, `GenerationId`, `UserId`, `ChatId`, `IdempotencyKey` (unique)
- `Status`, `Attempts`, `NextAttemptAtUtc`, `LeaseUntilUtc?`, `LeaseOwner?`
- `SessionVersionAtEnqueue`, `ReservedBudgetUsd`, `LastErrorCode?`
- `CreatedAtUtc`, `StartedAtUtc?`, `FinishedAtUtc?`

### `ImageUsageRecord`

- `Id`, `JobId` (unique), `UserId`, `ChatId`, `Model`
- `InputTextTokens?`, `InputImageTokens?`, `OutputImageTokens?`
- `EstimatedCostUsd`, `ActualCostUsd?`, `PricingVersion`, `CreatedAtUtc`
- Не путать оценку с точным списанием провайдера; при отсутствии usage сохранять флаг `CostIsEstimated`.

Индексы: активная сессия `(ChatId, UserId)`; сообщения `(ChatId, MessageId)`; список сессий `(OwnerUserId, UpdatedAtUtc)`; job `(Status, NextAttemptAtUtc)`; уникальный idempotency key; история `(SessionId, CreatedAtUtc)`.

### Хранилище файлов

Для небольшой компании допустимо локальное persistent storage/volume; за API `IImageAssetStore` предусмотреть замену на S3-совместимый storage. Не класть большие бинарные изображения в PostgreSQL без особой причины. Файлы должны переживать рестарт контейнера. Применять безопасные UUID-имена, проверять фактический тип и размер, исключить traversal. Старые assets удалять фоновым retention job только если нет живых ссылок из разрешённой истории.

## 7. Очередь, состояние и конкуренция

- В MVP достаточно одного worker внутри приложения и **персистентной** очереди в используемой БД. Не добавлять Redis/RabbitMQ только ради этой функции.
- Ограничить глобальную параллельность (по умолчанию 2), параллельность на пользователя (1) и на сессию (1). Значения конфигурируемые.
- Telegram update handler отвечает быстро: запись job → сообщение «В очереди / обрабатываю» → фоновая работа → публикация результата.
- На рестарте восстанавливать job из БД; использовать lease/heartbeat и защиту от двойного захвата.
- Повторяемые ошибки `429`/временные `5xx` — exponential backoff с jitter и ограниченным количеством попыток. `401`, ошибки параметров, модерация — без бессмысленных повторов.
- Если исход внешнего вызова неизвестен после сетевого обрыва, **не делать автоматический повтор, потенциально приводящий к двойной оплате**, без корректного механизма идемпотентности у провайдера.
- Отдельно обрабатывать невозможность отправить ответ в Telegram: не генерировать изображение заново, а повторить только публикацию готового asset.
- Протоколировать переходы статусов, но не логировать изображение, API-ключ и полный промпт без необходимости.
- Reset в гонке с completion не меняет указатель новой сессии; проверяется версия/статус при транзакционном обновлении.

## 8. Лимиты и денежные ограничения

Реализовать на уровне приложения, **не полагаясь только на лимиты аккаунта OpenAI**:

- whitelist разрешённых Telegram `UserId` и/или `ChatId` (если существующая система прав уже есть, интегрироваться в неё);
- дневное число заявок на пользователя (стартовый пример — 5, конфигурируемо);
- глобальный дневной/месячный лимит количества заявок;
- конфигурируемый оценочный бюджет в USD на пользователя и на бот;
- ограничение количества ожидающих задач, количества референсов и размера файла;
- попытка **зарезервировать** бюджет до enqueue; снять резерв при гарантированно неисполненном job или сверить с фактическим usage при завершении;
- защитить счётчики транзакциями/конкурентными обновлениями, чтобы параллельные запросы не обходили бюджет;
- при исчерпании квоты показывать понятное сообщение и время до следующего сброса (временная зона счётчиков явно задаётся, по умолчанию UTC);
- тарифные ставки и их версию хранить в настройках, не зашивать навсегда в исходный код; считать по фактическим токенам, когда доступны;
- в `/usage` различать примерную локальную стоимость и реальный биллинг OpenAI.

Пример `ImageGeneration` configuration (адаптировать к системе настроек проекта):

```json
{
  "ImageGeneration": {
    "Enabled": false,
    "DefaultModel": "gpt-image-2.6-flare",
    "HighQualityModel": "gpt-image-2.6-sunburst",
    "DefaultQuality": "medium",
    "DefaultSize": "1024x1024",
    "MaxInputImages": 4,
    "MaxInputFileMb": 15,
    "MaxConcurrentJobs": 2,
    "MaxConcurrentJobsPerUser": 1,
    "DailyJobsPerUser": 5,
    "RetentionDays": 30,
    "StoragePath": "./data/image-generation"
  }
}
```

`OPENAI_API_KEY`, Telegram token и другие секреты — только через существующую безопасную конфигурацию (env/user-secrets/secret store). Пустой ключ или `Enabled=false` должны отключать модуль с понятной диагностикой без падения всего бота.

## 9. Интеграция OpenAI и подготовка промптов

- Модель выбирается по текущей разрешённой настройке пользователя, с fallback на доступную модель по умолчанию.
- Первичная генерация — Images Generations; редактирование — Images Edits с одним или несколькими входными изображениями.
- Для edit не терять пользовательскую инструкцию. Дополнительные указания о сохранении лица, света, композиции и т.п. применять только когда это соответствует запросу/режиму, не навязывать их каждому запросу.
- Выход по умолчанию `1024x1024`, `quality=medium`; размер и качество — конфигурация с валидацией по возможностям модели.
- Результат получать как бинарные данные, проверять MIME, сохранять в asset store, только потом отправлять в Telegram.
- Поддержать входные `png`, `jpg/jpeg`, `webp` при фактической поддержке endpoint; ограничения Telegram и OpenAI проверять раздельно.
- Использовать стабильный, неперсональный `safety_identifier`, например хеш Telegram user ID с серверной солью.
- Ошибки модерации обрабатывать человеческим текстом без раскрытия внутренних подробностей и без попыток обхода ограничений.
- Не обучать/настраивать собственную модель; не реализовывать локальное редактирование через CPU/GPU.

Полезная документация:

- OpenAI Image Generation: https://developers.openai.com/api/docs/guides/image-generation
- OpenAI Image Edit API: https://developers.openai.com/api/reference/resources/images/methods/edit
- OpenAI API Pricing: https://developers.openai.com/api/docs/pricing
- Официальный OpenAI .NET SDK: https://github.com/openai/openai-dotnet
- Telegram Bot API: https://core.telegram.org/bots/api

## 10. Права, приватность и удаление

- Любой участник группы может использовать изображение, **уже явно опубликованное в этой группе**, как основу собственной ветки при наличии доступа; это не даёт ему доступа к истории автора, личным сообщениям или неопубликованным assets.
- Результаты из лички другого человека никогда не открываются по угаданному GUID/callback data.
- Если автор удалил сообщение из группы, это не обязательно означает немедленное удаление asset с сервера; в `/help`/политике бота ясно объяснить хранение и срок удаления, предусмотреть явное удаление своей истории.
- Изображения реальных людей обрабатывать по применимым правилам сервиса; соблюдать политику OpenAI, не обходить её фильтры.
- Все файлы скачивать только по идентификаторам Telegram/проверенным источникам; не принимать произвольный URL из промпта как команду на серверное скачивание.
- Не допускать XXE, SSRF, path traversal, zip bombs, чрезмерного потребления памяти при декодировании изображений. Ограничивать пиксельные размеры, bytes и время обработки.
- Логи не должны содержать Telegram bot token, OpenAI API key, приватные файлы и base64-изображения.
- По умолчанию срок хранения assets 30 дней; конфигурируемо. Удаление данных не должно каскадно уничтожать ещё используемые чужие ветки без осознанной политики ссылок.

## 11. UX, ошибки и локализация

- Тексты интерфейса — на русском; централизовать, не разбрасывать строки по обработчикам.
- Все долгие операции имеют статус: «в очереди», «генерирую», «готово», «не получилось».
- Если нет изображения для edit, объяснить: «Пришли фото с подписью или ответь командой `/edit` на картинку».
- Если пользователь без прав, отвечать кратко без раскрытия секретных настроек.
- При `429`/очереди показывать понятное ожидание, но не обещать точное время готовности без измерений.
- Отправлять быстрый preview в `sendPhoto`, а качественный оригинал — по кнопке через `sendDocument`; если результат слишком большой, обрабатывать ограничения Telegram.
- В группе ответы адресовать инициатору/исходному сообщению и избегать флуда; не отправлять многократные одинаковые статусы.
- Inline-кнопки старых сообщений должны безопасно реагировать на закрытую/удалённую сессию.

## 12. План работ / backlog

### P0 — MVP, реализовать обязательно

1. Аудит архитектуры существующего бота и выбор точек интеграции.
2. Конфигурация, DI, feature flag, права пользователей/групп.
3. Миграции БД: сессии, генерации, assets, ссылки на Telegram сообщения, jobs, usage.
4. Хранилище файлов с persistent volume; скачивание/валидация Telegram photo/document.
5. `/imagine`, `/edit`, фото с подписью, личка и группа.
6. OpenAI adapter + fake provider для тестов; модель, качество, размер из конфигурации.
7. Персистентная очередь с корректной обработкой рестарта и повтора отправки в Telegram.
8. Активная сессия, последовательное редактирование, `/reset` и кнопка сброса.
9. Reply на конкретный результат и ветка от чужого **публичного** результата.
10. Лимиты, локальный учёт расходов, защищённое резервирование бюджета.
11. Обработка отказов/moderation/429, логирование, русские сообщения пользователю.
12. `/help`, базовый `/usage`, краткая документация запуска и тесты критических сценариев.

### P1 — после устойчивого MVP

1. Альбомы с 2–4 референсами, управление черновиком/добавление референса.
2. `/history` с постраничной навигацией, восстановлением старой сессии и просмотром графа веток в текстовом виде.
3. `/settings` с качеством, форматом и профилями.
4. Кнопки «Переделать», «Оригинал» и расширенные действия под результатом.
5. Автоматический retention/cleanup и пользовательское удаление истории.
6. Улучшенная аналитика расходов, суточный сводный отчёт администратору.

### P2 — будущие улучшения

1. Responses API для многошагового диалога при доказанной пользе.
2. Различные пресеты мемов/стилей и библиотека промптов.
3. Веб-галерея, экспорт веток, S3 storage.
4. Более точное управление зонами редактирования (маски/разметка).

P1 не должен блокировать P0. Если масштаб задачи велик, Codex сначала завершает P0 и предоставляет работающий вертикальный срез, а не оставляет набор непроверенных абстракций.

## 13. Проверки и критерии приёмки P0

### Функциональные

- [ ] В личке `/imagine` ставит ровно один job и публикует сгенерированный результат.
- [ ] Фото + промпт запускает edit; результат можно ещё раз изменить обычным текстом в личке.
- [ ] В группе обычная переписка не запускает AI; явная команда и Reply работают.
- [ ] У двух пользователей одной группы независимые активные сессии.
- [ ] У одного пользователя личка и группа имеют независимые сессии.
- [ ] Reply на старое сообщение бота продолжает **именно** тот узел истории.
- [ ] Reply на чужой результат в группе создаёт отдельную ветку и не меняет сессию автора.
- [ ] Нельзя получить приватный результат другого пользователя через callback или подмену GUID.
- [ ] `/reset` и кнопка сбрасывают только сессию инициатора в соответствующем чате; старые результаты сохраняются и доступны через Reply на сообщение бота до истечения срока хранения. Отдельный интерфейс `/history` — P1.
- [ ] Завершение старого job после reset не подменяет новую активную сессию.
- [ ] Повтор Telegram update/callback не приводит к двойной генерации.

### Надёжность и деньги

- [ ] Перезапуск процесса не теряет jobs и файлы; восстановление не создаёт лишние платные вызовы.
- [ ] На пользователя/сессию соблюдается установленная параллельность.
- [ ] Два одновременных запроса не обходят лимит/бюджет из-за гонки.
- [ ] Ошибки OpenAI, нехватка кредитов, модерация и невозможность отправки Telegram корректно обрабатываются.
- [ ] Повтор отправки готового результата в Telegram не вызывает повторной генерации.
- [ ] Пользователь видит расходы как оценку, когда нет подтверждённых данных usage.
- [ ] Секреты и содержимое картинок отсутствуют в логах.

### Инженерные

- [ ] Сборка и запуск по документированным командам.
- [ ] Миграции применяются к тестовой БД без потери существующих таблиц.
- [ ] Unit/integration тесты на сессии, reset race, Reply routing, авторизацию веток, идемпотентность и квоты с фейковым провайдером.
- [ ] Нет платных вызовов OpenAI в автоматических тестах.
- [ ] Существующие модули/команды бота продолжают работать.
- [ ] Конфигурация контейнера и persistent volume документированы.

## 14. Definition of Done и формат ответа Codex

Результат считается готовым, когда P0 реализован, собран, проверен тестами, конфигурация и миграции документированы, а новые функции отключены безопасным флагом до явного включения владельцем.

Отчёт Codex должен включать:

1. Краткое описание обнаруженной архитектуры существующего бота.
2. Что реализовано и что перенесено в P1/P2.
3. Перечень изменённых/добавленных файлов и основных сервисов.
4. Инструкции настройки OpenAI API key, Telegram, БД, хранилища и лимитов **без публикации реальных секретов**.
5. Команды миграции, локального запуска и тестов.
6. Результаты фактически выполненных проверок, известных ограничений и потенциальных рисков стоимости.

**Начни с анализа репозитория и плана. Затем реализуй P0 небольшими проверяемыми этапами. Не делай реальный API-запрос и production deploy без разрешения.**
