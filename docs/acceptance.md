# Проверки и приёмка

## Выполнено локально

- `dotnet build -c Release` — успешно, без предупреждений и ошибок.
- `dotnet test -c Release` — без реальных Telegram/OpenAI вызовов.
- Запуск с настройками по умолчанию — понятное отключение без сети API.
- `dotnet run --project DerevenkaBot -- --migrate` — успешно на локальной БД.
- Повторные миграции и восстановление БД/файлов — интеграционные тесты.
- `docker compose config --quiet` — конфигурация корректна.
- NuGet audit с транзитивными зависимостями — известных уязвимых пакетов не найдено при проверке.

## Автоматические сценарии

`ImageModuleTests`: единственный job на повторный update; изоляция пользователей и чатов; точная ветка Reply на старый публичный результат; reset во время работы провайдера; конкурентные квоты/резервы; восстановление очереди и файлов; Unknown после истечения lease без нового вызова; повтор Telegram-доставки без генерации; игнорирование обычной переписки и чужой bot-команды; фото с подписью → продолжение через `/edit`, обычный текст игнорируется; поддельный приватный callback; сброс только инициатора и идемпотентность кнопки; запрет чужого asset по угаданному GUID; отклонение не-изображения; безопасные переходы при ошибках провайдера.

`ChatTests`, `OpenAiChatProviderTests` и `TelegramAiDraftTests`: `/chat` → Reply в личке и группе, обычный текст игнорируется; история и маршрутизация Reply после перезапуска; изоляция пользователей/чатов, reset и отзыв доступа во время запроса; сохранение готового ответа и повтор Telegram-доставки без вызова модели; разбиение длинного ответа и экранирование; потоковый текст до завершения HTTP-запроса и до финальной публикации; один стабильный draft ID; сохранение через `sendRichMessage`; fallback и `retry_after`; ошибка/обрыв SSE не принимаются за успешный ответ и не повторяют запрос.

Параллельность чата проверяется с заблокированным fake-провайдером: разные пользователи и разные чаты одного пользователя одновременно начинают запросы, общий предел соблюдается несколькими worker, один диалог выполняется в FIFO с правильным контекстом. Hosted worker действительно запускает несколько слотов. Интеграция с `TelegramPollingWorker` через настоящий SDK и fake HTTP подтверждает, что новый `getUpdates` и сохранение offset продолжаются при двух незавершённых ответах. Дополнительно проверяются сохранность очереди после перезапуска, отмена старой очереди при reset без задержки нового диалога, отзыв доступа, backoff доставки без блокирования других диалогов и восстановление истёкшего lease без повторного платного вызова.

`OpenAiAdapterTests`: поля конфигурации и исходная инструкция в JSON/multipart; коллекция input images; бинарный результат и usage; 400/401/429/500; сетевой обрыв без повторов и без утечки исходной ошибки.

`AccessTests`: закрытый доступ по умолчанию; владелец; постоянное групповое разрешение с изоляцией от лички; личное разрешение; запрет выдачи обычным участником/администратором; защита от повторной старой команды отзыва; отмена ожидающих задач и возврат резерва; независимые user/chat разрешения; отзыв начального allowlist; приватность списка и валидация целей.

`TelegramGatewayTests`: настоящая библиотека Telegram.Bot с подставным HTTP transport — SendMessage с Reply и SendPhoto с безопасным callback. Никакой сети Telegram.

Главное меню проверяется в личке и группе: первые кнопки «Чат» и «Картинки», раздел изображений содержит создание, редактирование и возврат. Нажатие «Чат» только открывает подсказку, повтор callback не создаёт её копию, обычный текст не вызывает модель, а ответ на подсказку запускает диалог. Переход к картинкам закрывает ожидающий вопрос чата и позволяет создать изображение. Сохраняются проверки доступа, выключенного чата и адресное ForceReply в группе.

`TelegramCommandMenuTests`: регистрация обычных и русских списков команд через настоящий SDK с подставным HTTP; команды управления только в приватном scope владельца; сохранение команд других модулей; общее меню доступно даже при ошибке личного меню владельца; выключенный модуль или авторегистрация не выполняют API-вызовов. Настоящее обновление меню в Telegram при разработке не запускалось.

Автогенерация `SafetySalt` проверена отдельно: создание и повторное использование после перезапуска, параллельный старт, сохранение ручного значения, отсутствие файлов в fake/выключенном режиме, понятные ошибки для короткого значения и повреждённого файла.

Дополнительно проверена выдача доступа по короткому ID и полному `user ID` из группы/лички, по Reply и через адресованную боту команду. Невладелец не может выдавать доступ. Reply на пересланное сообщение использует только видимого исходного автора; пересылка со скрытым автором не выдаёт доступ переславшему. Выдача и отзыв по Reply проходят проверку сервиса и маршрутизации Telegram без запуска генерации.

Отключённые квоты дополнительно проверены 12 одновременными новыми заявками при числовых порогах в 1 запрос и бюджете меньше стоимости одной заявки: все приняты, usage сохраняется, `/usage` показывает отсутствие квот. Прежний тест конкурентной защиты квот явно включает `LimitsEnabled=true`.

Новые сценарии UX проверяют ветвление по кнопке «Продолжить» от точного результата, выдачу сохранённого оригинала без нового вызова провайдера, доступ к приватным результатам, идемпотентность, ввод описания/ID через ForceReply с TTL и авторизацией инициатора, сброс ожидающих подсказок. Проверены обновление единственного статусного сообщения, безопасная работа при ошибках необязательного UI, HTML escaping конфигурации и недоступность административных callback для невладельца. Через настоящий Telegram.Bot с fake HTTP проверяются `sendRichMessage`, цветные inline-кнопки, `copy_text`, HTML parse mode, ForceReply и текст callback без HTML в пределах лимита Telegram.

Команды `/imagine`, `/edit`, `/ai_allow`, `/ai_revoke` без аргументов открывают подсказку. Фото без подписи в группе вызывает ForceReply; ответ редактирует сохранённый черновик. Повтор исходного Update не создаёт вторую подсказку.

Повторная UX-проверка покрывает ввод ID в личке без Reply, завершение шага после успеха, ошибки ID без запуска AI, видимые/скрытые авторы пересылок и команды в тексте пересланного сообщения, продолжение выбранного старого результата обычным следующим сообщением, защиту нового шага от старой кнопки отмены, сохранность jobs/сессии при отмене ввода, игнорирование групповой переписки при открытом шаге, инструкцию Reply на обычное фото и сценарий «Изменить» без исходника. Fake HTTP проверяет inline ForceReply с отменой, редактирование Rich-панели и успешный no-op при неизменившейся карточке.

Native AI drafts проверены через fake HTTP настоящего Telegram.Bot: Thinking и стабильный ненулевой draft ID, отсутствие кнопки Stop, обычный chat action для групп/выключенной функции, fallback при неподдерживаемом endpoint и пауза по `retry_after`. Существующий тест необязательных UI-ошибок подтверждает сохранение успешного результата без повторного вызова провайдера.

Заявки на доступ: проверены конкурентная дедупликация, личный scope, одобрение и сохранность разрешения после рестарта, отказ без изменения независимых разрешений, проверки владельца/чата, гонка одобрения и отклонения, старые кнопки после отзыва и после новой заявки, ручная выдача доступа при ожидающей заявке, восстановление уведомлений после ошибок и перезапуска, полный путь от `/start` без доступа до кнопки решения и уведомления, отсутствие image jobs. SDK-тесты проверяют адресата владельца, безопасный callback, HTML escaping профиля, кнопку заявки и переход из группы в личку.

Регрессия двойного прогресса проверена отдельно: native draft удаляет обычный статус, поздний ACK не возвращает его, fallback восстанавливает ровно одну карточку, одинаковые тексты не редактируются повторно, ошибка после draft остаётся постоянным сообщением, поздняя очередь не заменяет ошибку, конкурентные UI-обновления не создают дубликаты. SDK-тест подтверждает идемпотентность удаления уже удалённого статуса.

## Ещё не проверено внешне

- Настоящий токен Telegram: доступ бота в личку/группу, privacy mode, доступные Update и доставка больших файлов.
- Настоящий OpenAI key: доступность моделей организации, реальные изображения, модерация, квоты и формат фактического usage.
- Сборка и запуск Docker-образа: Docker CLI доступен, но Linux daemon на машине не запущен. Проверена только конфигурация compose.
- Нагрузочная эксплуатация и принудительный crash процесса в произвольной инструкции. Автотесты моделируют рестарт по персистентному состоянию и истечение lease.

Это локально проверенная реализация основного пути P0, а не утверждение о завершённой production-приёмке всех пунктов ТЗ. Осознанные отклонения и эксплуатационные ограничения перечислены в [architecture.md](architecture.md); P1/P2 — в README и исходном ТЗ. Внешний smoke test и развёртывание владелец выполняет отдельно после настройки разрешений и лимитов.
